# Company and section policy core

`features/access/policy.ts` computes permissions from trusted current policy facts. It does not persist policy or replace the existing workspace membership checks. UI, domain commands, PostgreSQL policies, invitation acceptance and MCP must use the eventual adapter before arbitrary section sharing can be described as enforced.

The canonical tree has an organization root, spaces directly below an organization, nested sections below organizations/spaces/sections, and workspaces below spaces or sections. A workspace is a leaf in this policy tree; its task authorization remains the workspace domain's responsibility. The maximum depth is 16 parent edges. Each resource has exactly one canonical parent. Cycles, missing parents, duplicate IDs, malformed grants and invalid hierarchy fail closed.

Policies are allow-only. `inherit` unions inherited capabilities with explicit current-resource grants. `restricted` clears ancestor grants and starts from explicit grants on that resource. Inherited read-only access stays read-only unless a matching explicit grant adds capabilities. Every grant explicitly includes `read`; `create`, `edit`, `comment`, `manage` and `delete` are independent. Manage is permission to manage that resource's policy, not a content-edit permission or a bypass into restricted descendants. Owners and administrators need explicit grants and have no hidden bypass. Any future recovery mechanism must be separately authorized and audited.

User and group IDs are stable identifiers from trusted identity records. Group grants match only active group memberships scoped to the target resource's canonical organization. Company membership alone grants no content permission. Explicit grants on a contained resource may authorize its inheriting subtree while ancestors remain inaccessible. Deeper restricted boundaries still apply.

A canvas reference is placement, not containment or authority. Adding, moving or receiving a reference does not grant access to its target. An invitation is a proposal, not a grant: accepted sharing must explicitly create an audited grant on the intended contained resource. The resulting grant then follows the same inheritance rules. The existing workspace invitation mechanism remains unchanged until a policy-aware adapter is implemented.

Agent and external application authority uses the existing verified `platform_delegations` connection model. Its current action capabilities, workspace scope, expiry and revocation are intersected with the human's current membership and section permissions on every dispatch. The ACL module accepts only the verified human actor and has no second delegation table or agent-token binding. Agents cannot create authority by claiming a human identity, group membership or a canvas reference. Scoped applications receive only their selected readable workspaces and already-readable canonical ancestors; they cannot invoke global company management.

The resolver returns capabilities in a canonical order and no hidden ancestor metadata. A missing or malformed authorization graph never becomes an empty-but-successful policy. Existing workspaces without a section retain the current membership and owner/creator/assignee rules through a future compatibility adapter; this module does not reinterpret them.
